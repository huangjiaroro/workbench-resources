# 项目维护：连续性、反馈诊断与定向返修

适用于整体 Blueprint、Canon、Story Unit 或长期设计出现事实矛盾、人物长线失效、单元重复、系列引擎疲弱及其他需要定向修订的问题。

## 连续性与上下文

### 当前任务的上下文

上下文应服务于当前问题。设计或修订某个 Story Unit 时，聚焦其人物、已采用的整体结构、适用的世界规则、前后事件与尚未回收的铺垫。不要把尚未采用的候选方案当成项目事实。

### 事实与状态

维护会影响后续叙事的时间顺序、行动条件、世界规则、人物状态、知识与误信、关系、秘密和未解决命题。区分**客观已发生事实**、**角色暂时相信的事实**、**已经采用的未来规划**和**未采用的创意候选**。信息缺失不自动构成矛盾，判断以有效成果为依据。

## 项目级反馈怎样定位

收到“故事不成立”“单元重复”“人物没成长”等反馈时，先区分三类信息：

- **问题现象**：读者观察到的重复、断裂、无因果或无变化，需有具体情节作为证据。
- **建议修法**：例如换一位反派、删掉一个单元、提前揭示秘密；它是候选方案，不等同于问题根因。
- **硬性要求**：用户已锁定的创作方向、关键事件、结局、世界规则等，属于修订的有效约束。

根据证据确定真正受影响的设计层：

| 问题层级 | 典型诊断 | 对应专业入口 |
| --- | --- | --- |
| 核心前提与整体因果 | 事件虽然热闹，但关键转折与结局缺少因果 | [故事结构](story-structure/craft.md) |
| 人物长期对抗与弧线 | 人物欲望、选择或对手压力不能支撑长期变化 | [人物与长期冲突](character-arc/craft.md) |
| 单元重复与冲突枯竭 | 不同单元只替换人物，却重复同一种冲突机制 | [系列引擎](series-engine/craft.md) |
| 季线与分集组织 | 单元位置、信息释放或主副线推进相互抵消 | [整季与分集结构](season-structure/craft.md) |

## 方案比较与影响核验

当某个修法不适用时，保留它试图解决的**戏剧功能**（关键选择、压力升级、信息揭示、伏笔回扣或关系转变），再寻找能够承担同一功能、且不违背约束的替代设计。

抽象大纲争论难以判断时，可以局部试写某个单元的关键事件或人物选择，检验其是否真正产生新冲突；不必为了测试单元而重做整季。

确定修改范围时，先找到直接依赖，再追踪真正受到影响的 Blueprint、Canon、Story Unit、分集设计和有效正文。旧规划与新决定冲突时，明确被替代的是哪项决定；已发生的剧情事实不能因为上游大纲改写而自动消失。涉及用户锁定决定的变更由相应权限处理。

修订结束后核对原问题是否改善、故事长期因果是否仍成立、系列冲突是否有差异与升级、下游是否出现新的连续性矛盾。

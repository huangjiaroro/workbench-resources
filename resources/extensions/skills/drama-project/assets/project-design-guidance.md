# 整体故事设计稿

`project-design` 是整体开发过程中逐步形成、向用户和相关员工共享的正式设计产物，真实路径由当前产物契约解析。它保存设计推导、重要取舍与尚待解决的问题，支撑 Blueprint 和后续单集，与整体故事成果一并交付。首次整体开发按 `SKILL.md` 的阶段依赖开展设计并保存；既有设计可引用准确位置，局部修订只更新受影响部分。

## 采用方案需要具备的设计内容

按当前故事的事件、人物关系和采用方案组织设计稿，不要求用 P1–P4 作章节名。下表将设计内容关联到方法入口，具体正文由模块索引选择，读取与复用遵循[技能入口](../SKILL.md)；表格不规定作品章节或阅读记录。

| 设计范围 | 应形成的实质内容 | 方法入口与选择条件 |
| --- | --- | --- |
| 故事核心、整体因果与高潮 | 核心事件怎样迫使人物行动；关键选择、反制和代价怎样导致后续转折；高潮与结局怎样兑现前面的因果、关系与伏笔。不能只罗列开端、几个大场面和结局。 | [故事结构索引](../references/story-structure/index.md)：按前提、事件因果、转折或高潮问题选择正文；需要具名结构体系时由该索引定位对应理论。 |
| 承重人物、长期冲突与弧线 | 主角、主要对手及持续改变主线的关键配角各自追求什么、有什么手段和制约；目标如何冲突、相互依赖，失败或成功后如何改变策略；压力怎样升级，关键选择怎样改变关系、认知或处境。变化可以是成长、堕落或坚持，不要求人人正向成长。 | [人物与长期冲突索引](../references/character-arc/index.md)：发展欲望、对手、压力升级和关键选择；复杂动机或态度突变再选心理学与冲突案例。 |
| 连续作品的故事引擎 | 哪些人物关系、行动约束和事件机制持续产生冲突；推演关键事件的不同策略、结果及后果怎样积累；已有优势为什么不能立即解决全部问题；引擎怎样升级、转向或闭合。身份信息差、类型标签或“每集有爽点”不能单独代替事件生成机制。 | [系列引擎索引](../references/series-engine/index.md)：选择事件模式、人物网络及升级方法；冲突重复或主角优势使对抗失压时，进入其诊断与变奏资料。 |
| 整季、单元与分集推进 | 各阶段承担的目标、关系或局势变化，以及阶段之间的因果；关键集和承重单元的独特作用、信息揭示、伏笔与兑现；足以支持当前单集的前后承接。无需提前写完全部单集，也不按固定时段公式代替剧情设计。 | [整季与分集索引](../references/season-structure/index.md)：按季线、分集作用、信息管理、多线编织和悬念选择正文及案例。 |

人物范围由其对故事的作用决定。持续承担对抗的反派及其与主角、同盟的关系必须进入设计；其动机、策略和压力不能只用“恶毒”“嫉妒”或最终下场带过。不为无承重作用的小角色补造完整传记，也不强行增加人物数量。

## 取舍、继承与表达

对决定主线走向、长期对抗或关键揭示的重要选择，保留为什么采用、它解决了什么问题，以及会带来什么代价；确有实质候选时说明取舍，不为每个细节强造多套方案。未解决且影响后续设计的问题写明影响范围。

采用专业理论时，体现它怎样影响了当前人物、转折或机制的选择；只填理论的步骤名、给现成故事加术语标题不算设计推导，也不需要为了显示专业而硬套具名体系。

用户要求、作者或主创采用的故事方案、人物当时所知、未来规划和未采用候选要能区分。将采用方案整理为 Blueprint、Canon 时保留其实际来源，不能把自定情节或节奏建议归入用户硬约束。设计变动时同步直接依赖；已在其他有效设计中说清的内容可准确引用，避免维护两套相互矛盾的正文。

**格式自由**：不规定标题、字数、表格、章节顺序或四份独立文件，不单独增加主创审批。内容必须体现实际设计，不能用性格形容词、剧情摘要或方法名清单代替行动与因果。
